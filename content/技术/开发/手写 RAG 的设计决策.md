我在给自己的笔记建一套 RAG 系统。动手之前先写了一份开发文档，252 行，里面没有一行代码。

这篇不是教程。我是想把那份文档里几个真正的决策摊开讲——它们单看都很像常识，但每一条我都能说出"不这么写会怎样"。

### 为什么不用框架

文档的第一条设计原则是这个：

> **不用 LangChain / LlamaIndex（第一阶段）**：本项目以理解 RAG 全链路为目的，Pipeline 手写实现；理解后再评估是否引入框架。

重点在**"第一阶段"**。

如果它只写到"不用框架"，那它就是一句立场，甚至有点姿态。因为用框架省掉的那部分工作——文档加载、切分、向量库适配、链式编排——LangChain 确实帮你写了；而"框架会遮住细节"这个理由单独拿出来也不成立，细节被遮住不等于你不能去看源码。

让它从**立场**变成**决策**的，是后半句：**理解后再评估**。这句话给这个选择设了一个退出条件——等我把检索、重排、上下文拼接都亲手写过一遍，再回头看框架提供了什么，那时候的判断才有依据。

区别在这里：有退出条件的选择可以被推翻，没有退出条件的选择只能被坚持。

### 验收标准必须能被验证

每个 Phase 都有四栏：目标、任务、交付物、**验收标准**。最后一栏是整份文档花力气最多的地方。

对比两种写法：

- ❌ 完成数据库层
- ✅ `alembic upgrade head` 成功；psql 中 `\d document_chunks` 可见 `vector` 类型列；`/api/health` 的 database 字段变为真实连接状态
- ✅ 对"Redis 支持哪些数据类型"的检索，相关 chunk 排名靠前，不相关文档得分显著更低

第一句读起来也像那么回事，但它不能被检验——你只能在心里点头，没法证明它成立。而后两句一个能用命令跑出来，一个能从检索结果看出来。

我给自己定的规则是：**验收标准全部通过，才允许标记完成并进入下一阶段。** 这条规则只有在验收标准本身可观测时才有效，否则它只是给自己发一张通行证。

### 指标不回退，是前提不是目标

质量评估那一节里有句话，是整份文档我最看重的：

> **指标不回退是后续所有优化的前提。**

因为 RAG 后面全是超参数：chunk_size 取 500 还是 800、overlap 取 100 还是 200、Top-K 取 5 还是 20、要不要上 reranker、用哪个 embedding 模型。这些调完**一定会"感觉更好"**——你调的时候心里已经知道想要什么结果了。

所以评估集必须建在优化之前。文档规定 Phase 7 完成后就建立 `tests/eval/questions.json`（问题 → 期望命中文档），之后每次改动跑三件事：检索命中率、回答有没有编造、回答有没有答到点上。

顺序反了，你就没有 baseline，所有"优化"都只是感觉。

### 把耦合写进代码

Embedding 模型输出 1024 维，所以数据库列是 `vector(1024)`。这个数字一旦落进 schema，就和模型绑死了。文档为此专门写了一条：

> 维度常量集中在 `app/models/document.py` 的 `EMBEDDING_DIM`，换模型必须连同迁移与全量重嵌入一起处理，**禁止只改常量**。

这条的价值不在于它说了什么，而在于它把一件"人必须记得的事"变成了"代码里能看见的事"——以后我想换模型，会在改常量的时候撞上这段话。同一个思路在风险清单里也出现了一次：换 embedding 模型会导致维度不匹配，缓解措施是**在 metadata 里记录模型名**。

### 阶段顺序本身就是设计

Phase 4 是 Chunking，Phase 5 是 Embedding，看起来就是自然的流程。但文档对 Phase 4 多加了一条：

> 交付物：`app/rag/chunker.py` + 单元测试（**不依赖数据库，纯函数测试**）

这条才是重点。切分是整个流水线里最容易出错的部分——边界怎么切、overlap 会不会重复、超长文本怎么处理、空文本怎么办。而它恰好可以写成纯函数：不需要数据库、不需要模型、不需要网络。

也就是说，**最难调的部分被安排成最容易测的部分。** 阶段顺序不只是流程图好看，它决定了每一层能不能被独立证伪。

### 预写退路

风险清单里有一条我一开始没在意：

> bge-m3 本地推理资源占用大 → 允许降级到 bge-small-zh；或改用 API Embedding

bge-m3 是个大模型，本地跑吃内存。关键不是"它大"，而是**我在动手之前就写好了退路**。等真的跑不动那天，我要做的不是临时决策，而是执行一个已经想过的方案。

预写退路的成本几乎为零，收益是避免在最累的时候做判断。

### 一个 .gitignore 的教训

Phase 0 里留了一段历史记录，值得单独拎出来：

> 初版 `.gitignore` 写了 `.md`（会忽略全部文档）却没忽略 `.venv/`（4000+ 文件差点入库）。**.gitignore 必须在第一次 commit 前审一遍。**

这个错误很典型。`.gitignore` 是个**反向**文件——你在列举"不要什么"，而漏掉一项是静默的，git 不会提醒你"这里少写了一条"。同时它又很容易顺手忽略掉你真正想版本化的东西：我当时写 `.md` 大概是想着排除草稿，可那些 Markdown 恰恰是这个项目的输入数据。

所以 git 规范里接着写了一条：首个提交前必须确认 `.gitignore` 覆盖 `.venv/`、`.env`、`__pycache__/`。凭直觉写一定会写错，得对清单。

### 这份文档还欠一个验证

得说实话：项目现在停在 Phase 2。

Phase 0 到 2 的验收标准是真跑过的，所以"写得足够具体就能执行"这件事在那三段上有证据。但 Phase 3 到 10——尤其是"检索排名靠前""回答基于检索资料"这种偏主观的——**还全是我的预判**。它们写得再具体，也还没被任何一次真实运行验证过。

所以这份文档目前只能这样说：**它在低不确定性的阶段有效，在高不确定性的阶段是一种愿望。** 后者的可靠性，得等我真走到那里才知道。

另一个已经能看到的代价：手写 pipeline 换来的是"知道每一层在哪"，失去的是"换一层时不用动别人"。以后加 reranker、换 embedding 模型，改动量会比用框架大。框架那层抽象这时候是省钱还是添乱，取决于那次改动的具体形状——我没法现在就下结论。
