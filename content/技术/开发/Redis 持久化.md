Redis 的持久化要回答两个问题：进程或机器出故障后，数据能恢复到什么时刻；恢复时要读多少东西。RDB 和 AOF 的取舍就在这里。本文讨论恢复点与读取量的机制，不提供无法复核的事故记录或压测数字。

## RDB：保存某个时点

RDB 把某个时间点的数据集写成二进制快照。后台保存通常由 `fork()` 出来的子进程完成，父进程继续处理请求；写操作触及共享页面后会触发写时复制，所以数据集越大、保存期间写入越多，内存和延迟压力越值得关注。快照文件紧凑，复制和异机保存都方便。

`save 900 1`、`save 300 10`、`save 60 10000` 是常见的触发条件写法，分别表示在相应秒数内达到写入次数后触发保存。它们描述触发规则，不承诺固定的数据丢失窗口：快照还没完成、磁盘故障或进程异常都会影响结果。

## AOF：记录写操作

AOF 把改变数据集的命令追加到日志，重启时重放日志。文件会增长，Redis 可在后台重写 AOF，用当前数据集生成较短的命令序列；这项工作也可能涉及 `fork()`。

`appendfsync` 决定何时要求把 AOF 同步到磁盘。`everysec` 通常每秒同步一次，是持久性与写入开销之间的折中；异常断电时仍可能丢失最近尚未落盘的数据，不能把“一秒”当作所有文件系统和硬件上的绝对上限。`always` 更频繁地同步，通常增加写入开销；`no` 把时机交给操作系统。实际延迟要在自己的工作负载和存储上测。

Redis 7.2 的 AOF 重写可使用 RDB 前导段，后接增量命令。是否启用、当前文件格式和启动时如何加载，须按实际版本与配置确认；不要把单个版本的默认值写成所有 Redis 的默认行为。

## 两者怎么选

RDB 适合定期快照、异机备份和较紧凑的恢复文件；AOF 提供按写命令恢复的路径，恢复时间会受日志大小和重放量影响。两种机制可以同时配置，但“双开”并不自动等于零丢失，也不能替代备份恢复演练。先确定业务可接受的数据丢失量和恢复时间，再选快照周期、同步策略与备份保留方式。

下面是 Redis 7.2 配置项的示意组合，具体值应按数据量、写入量和磁盘调整；它不是我的生产配置，也未在此环境实际运行：

```ini
appendonly yes
appendfsync everysec
aof-use-rdb-preamble yes

save 900 1
save 300 10
save 60 10000
stop-writes-on-bgsave-error yes
rdbcompression yes
rdbchecksum yes
```

`stop-writes-on-bgsave-error yes` 会在后台保存失败时拒绝写入，避免系统继续接受写入却让操作者误以为快照仍在更新。是否适合你的可用性要求，需要和告警及故障处理流程一起决定。至少监控最近一次 RDB 保存状态（如 `rdb_last_bgsave_status`），并定期验证备份能够恢复。

实际耗时和吞吐变化取决于 Redis 版本、数据集大小、写入模式、存储设备与配置，不能用“10GB 要几秒”或固定比例概括。做压测时应记录这些条件和恢复时间，RDB/AOF 才能在同一条件下比较。
