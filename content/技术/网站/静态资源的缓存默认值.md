title: "哈希文件可以长缓存，HTML 仍要重新校验"

站点跑在 Cloudflare Workers 上，字体、CSS、JS 全都是内容哈希命名、内容永不改变的那种文件，按理说它们最该被长期缓存。

我随手 `curl -I` 了一个字体分片，看到的却是：

```
cache-control: public, max-age=0, must-revalidate
```

`max-age=0, must-revalidate` 的意思是：浏览器可以用缓存，但**每次用之前都得先问一遍服务器**。实际发生的是 ETag 校验、返回 304——不算重，但也不是零。对一个永不改变的文件来说，这纯属浪费。

Workers 会在静态资源目录的根部找名为 `_headers` 的文件（无扩展名），用它的规则覆盖默认头。这个目录由 `wrangler.jsonc` 里的 `assets.directory` 决定，我是 `public`。

```text
/static/fonts/*
  Cache-Control: public, max-age=31536000, immutable

/*.css
  Cache-Control: public, max-age=31536000, immutable

/*.js
  Cache-Control: public, max-age=31536000, immutable
```

三条规则把字体和哈希过的 CSS/JS 全部改成一年 + `immutable`，HTML 不加规则，沿用默认的每次校验。

**只有内容哈希命名的文件才能给 immutable。** 我站里有个 `static/icon.png`，它没有哈希——如果我图省事写个 `/*` 把它也标成 immutable，那么以后我换了这张图，读者在一年内看到的还是旧图，而且**没有任何办法让他们刷新**。

这类事故的特点是：不会报错，不会有人告诉你，只是悄悄生效一年。所以我最后只对确实带哈希的三类文件下手，`icon.png` 保持默认校验。判断标准很简单——**文件名里有没有内容的指纹**。有，就能 immutable；没有，就只能老老实实校验。

`public/` 是构建产物，每次 build 都被清空重建，所以 `_headers` 不能直接放在里面，否则它会在下一次构建时消失，然后你毫无察觉地退回到默认缓存。我的做法是把源文件放在**仓库根目录**，再写一个 `scripts/copy-headers.mjs` 挂在 `postbuild` 上复制过去。

顺带一提，我还试过把 `_headers` 放进 `quartz/static/`，那是行不通的：Quartz 会把这一层的内容映射到 `/static/` 下面，而 `_headers` 必须待在**资源目录的根**。位置不对，文件在、规则不生效，一样是无声失败。

改完再 `curl` 一遍：

| 资源 | 结果 |
|---|---|
| 字体分片 | `max-age=31536000, immutable` |
| 哈希 CSS / JS | `max-age=31536000, immutable` |
| `static/icon.png`（无哈希） | 仍是 `max-age=0, must-revalidate` |

最后一行和前面两行一样重要——**“没有误伤”和“改对了”是同一件事**。

验证的时候我发现，`blrain.codes` 的 **HTML 请求**会被 Cloudflare 的机器人挑战拦下来（`cf-mitigated: challenge`，返回 403），但静态资源不受影响。这不是故障，但它决定了你能用什么方式验证自己的站点：curl 拿不到 HTML，也看不到 HTML 的响应头，而字体、CSS、JS 这些可以直接测；想确认页面内容，得走 GitHub Pages 那个镜像。也就是说，**能不能验证，本身也是部署架构决定的**。
