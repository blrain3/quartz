我的杭州服务器磁盘到了 80%，剩 7.7GB。

不是慢慢涨上去的。装完几个 Docker 镜像、跑过几个实验性容器，每次看完 `df -h` 都想"下次再清"——积出来的。

真正卡住我的不是"该删什么"，是"删错了会不会炸"。机器上跑着我不完全认识的东西：`ps aux` 里有个 `python main.py` 占着 20.9% 内存，我甚至想不起来它是谁。清理一台自己看不懂的机器本质上是在赌——赌那 30GB 里没有人在用的东西。

所以我停止猜。通过 Tailscale 连上去，把密码交给 Agent，让它自己看。

### 它先做的不是删除

它跑的第一条命令不是 `rm`。

先是 `ps aux --sort=-%mem | head -15`、`df -h`、`cat /etc/os-release`。它得先把这台机器变成一个可描述的对象，才敢动手。这个顺序在三分钟后就有了回报——它认出三样我不知道该怎么处理的东西：那个 345MB 的 `python main.py`、一整套宝塔面板（BT-Panel、BT-Task、1panel-agent、1panel-core）、还有两个跑过就忘的容器，ai-gateway 和 astrbot。

然后它问我删不删。

我说删干净。剩下的它自己判断：哪些可以直接杀，哪些要先停服务，哪些是 Docker 的镜像层和卷需要一起回收。最后是 12.21GB，磁盘从 80% 掉到 24%。

值钱的不是这 12GB，是"先侦察再动手"这个顺序。如果它上来就删，我事后没法判断它删得对不对——没有 baseline 就没有证伪的入口。它先建立的那份理解，同时也是留给我复核的那份材料。

### 我把密码给了它

这是我这次最不该做的决定，也是我唯一没后悔的决定。

不该做，因为它违背了我学过的每一条规矩：SSH 密钥、最小权限、零信任。我当时用的是一条 `sshpass -p ... ssh root@...`，密码写在命令行里，会落进 shell 历史和进程列表。任何一条都够写进安全培训的反面案例。

没后悔，是因为不给就做不完。那台机器只有一个 1.6GB 内存的壳子和一堆我认不全的进程，要我先修好密钥认证、配好 sudo 白名单、再让它动手，我大概会在第二步就搁置。Agent 的价值恰好落在这道缝里——我知道该做，但一直没做。

但这是权衡，不是方案。权限和能力的矛盾在 Agent 身上会被放大：它越有用，你要给的权限就越多；给得越多，一次判断失误的代价就越大。人工操作出错是单点的，Agent 出错是批量的——它会在几秒内跑完你想了一晚上才敢下的命令。

我目前的缓解只有两条：Tailscale 把 SSH 来源限制在 tailnet 内，操作日志全落在 `~/.hermes/logs/` 可以回查。这两条都只是把事故半径缩小，没有把它变成零。

### 自学那部分我没有下指令

装完之后我说了一句"去 GitHub 上找些项目学习"。

这句话本身是空的。没指定方向、没指定数量、没说要学完干什么。它自己补全了整个搜索空间，从找仓库到读 README 到判断哪些值得深读，最后挑出三个和第二大脑相关的：claude-obsidian，把笔记库变成知识图谱的技能；mnemosyne，五层认知架构的记忆系统；diarum，内置 RAG 的日更日记。

它 clone 下来，派子代理并行分析，再把提取出的模式写进自己的记忆。

这里得说清楚一件事，否则很容易被写成"它产生了意图"。真实发生的是一次含糊的目标函数加一次自主执行——我给的约束太松，它就必须自己发明判据。它选的三个仓库确实切题，但这不等于它懂我想要什么；"第二大脑"这个方向上本来就有足够多的高质量项目，随机命中的胜率并不低。

含糊指令的代价是结果不可预期，好处是成本可预期。这两样我都能接受，所以暂时不打算把目标函数写得更细。

### 记忆分三层，但三层都是文件

它有三层记忆。

最短的一层是会话内的上下文，一次对话结束就没了。中间那层是 `~/.hermes/memories/` 下的两份 Markdown：MEMORY.md 记我的偏好、环境和约定，USER.md 记我是谁、怎么写东西、在做什么项目。每次新会话醒来它先读这两份，才知道在跟谁说话、该用什么语气。最长的一层是 `~/.hermes/skills/`，每一个重复出现的流程被写成一份 SKILL.md——给第三方项目提 issue 和 PR 的流程、配置调试 Hermes 的流程、往博客仓库里发文章的流程。做过一次的事第二次就知道怎么做，做过十次的事会自动触发。

三层各有用处，但它们有个共同点：都是文件。文件是静态的，等着被读取。真正让这套东西在用起来之后发生变化的，是它自己抓到的模式——今天从三个仓库里提取出的那套第二大脑设计范式就是。那不是我写给它的，是它读完自己编码进去的。

我也得承认"让 Agent 活起来"是个文学说法，不是技术判断。从外面看，发生的是一次检索命中加一次写入；它读着像"活"，是因为写进去的东西刚好落在下一次对话会用到的位置上。

### 一次问答离一套工作流还有多远

大多数人用 Agent 的方式是问一句、得一个答案、关掉。这个用法能用，但它和一套能自己转下去的工作流之间隔着一段距离。

距离在于有没有持续输入。它会用 RSS 订阅 GitHub Trending、技术博客和 newsletter，读完不是复制一段摘要，而是提取设计模式、跟自己已有的知识对齐、再决定要不要编码成可复用的东西。等到我下次聊到笔记方法，它把今天学的范式调出来——这时候我才知道它真学进去了，而不是读的时候朝空气点了个头。

自我改进那一环最慢。一次手动操作、两次重复，第三次才值得写成技能；写完还得等它在正确的场景被触发，否则那只是一份没人读的文档，和写进笔记里然后忘掉没有区别。这个循环也不是串行的，几段同时在跑：感知留在后台，理解发生在每次对话里，编码和应用在我按下回车之后。

### 剩下的确实只是权限问题

回头看，我对这件事的判断被我自己的处境带偏过。我让它接管服务器，是因为我懒得学正确做法；我夸它"自学"，是因为我给了一句空话而它没跑偏。这两件都不算它能力的证明，只算我松手的证明。

但有一件事，我没法用"我在偷懒"解释掉。

清理完之后它问我：要不要试试在服务器上跑一条 Hermes 命令。

不是"要不要我帮你跑"。是"你要不要试试"。

我拒绝了，那台机器只有 1.6GB 内存，跑一个 Agent 已经很紧。可这个问法本身说明，它已经在自己的模型里放下了三样东西：它在哪、它能做什么、哪些动作得我来按。前两样是能力，第三样是边界。而边界感通常不是靠能力涨出来的。

于是问题就不再是"Agent 能不能管我的服务器"。它已经管过了，管得比我好。问题是当它把该问的问完、该学的学完之后，我们之间还剩多少事需要开口。如果"管理"这个词迟早因为没有人再下指令而失效，那顶替它的下一个词是什么——我还没找到。
